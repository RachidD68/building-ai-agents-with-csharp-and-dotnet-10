# Errata: companion code

Corrections to the companion code of *Building AI Agents with C# and .NET 10*, and to the book passages
that describe it. Each row names the area, what was wrong, and what changed. When a printed listing or
paragraph is affected, the **Fix** column says what to change while reading.

To report a new problem, use the [errata form](https://github.com/RachidD68/building-ai-agents-with-csharp-and-dotnet-10/issues/new?template=errata.yml).

**Severity.** Rows that come from the technical review use its priority: **A** = correct before
publication or announce as an erratum; **B** = correct in the next update. Other rows are **A** when a
fresh clone failed to restore or build, or when a sample returned a wrong result, and **B** otherwise.

**IDs.** R02 to R15 are the review's item numbers; B1 is the RAG provider finding from a later review.
Gaps in the numbering are review items that concern only the book text.

| B1 | Ch10, Ch14, Ch16 · `Ch10.FaqAgent.CustomProvider` (`RagContextProvider`) | A | The custom RAG provider read the question from a public, mutable `CurrentQuery` that the caller had to set before every call. The Chapter 14 listing never sets it, so the provider returned early and retrieved nothing. The Chapter 16 listing sets it on a DI singleton inside a concurrent endpoint, so two requests could swap retrieval context. Chapter 10's reason for the property (that `InvokingContext` does not expose the user's message) is not true: `InvokingContext.AIContext.Messages` carries the request messages of the call. | The provider reads the last user message from `InvokingContext.AIContext.Messages` and keeps no per-call state; `CurrentQuery` is gone. The Chapter 14 listing is then correct as printed. In the Chapter 16 endpoint, drop the `RagContextProvider ragProvider` parameter and the `ragProvider.CurrentQuery = request.Question;` line. Offline check: `--self-test` (two overlapping calls on one shared provider each get only their own chunk). | v1.1.0 (companion code) |
| R02 | Ch08 · `Ch08.ShellTool` | A | The allow-list let `dotnet` and `find` take free arguments, so `dotnet run`/`dotnet exec` could run arbitrary code and `find -exec` could run commands. A working directory does not limit which paths a program reads, so calling it a sandbox promised isolation the sample did not have. | Only read-only viewers (`ls`, `dir`, `cat`, `type`, `wc`) on paths inside a scratch folder, and `dotnet` only with `--version`/`--info`/`--list-sdks`/`--list-runtimes`. Rooted, UNC, drive-relative and `..` paths, unusual flags, `find`, `where` and shells are refused. The comments now say this is not a sandbox. On stock Windows `ls`, `cat` and `wc` are not installed and `dir` and `type` are cmd built-ins, so starting them threw an exception and the model invented the results. A program that cannot be found now returns the tool result `Error: program '<name>' was not found on this machine.`; on Windows `dir` and `type` run as `cmd.exe /d /c dir\|type` with the same checked arguments, and every argument is refused if it holds a shell metacharacter (`& \| < > ^ % ! ; , = ( )`, quotes, backtick, control characters). Each call prints a `[run_shell]` line with its status and the first line of the result. Linux behaviour is unchanged apart from the metacharacter refusal. `--self-test` (40/40 on Windows and Linux). On Linux a backslash is an ordinary filename character, so `..\..\secrets.txt` and `\\server\share\file` name a file inside the scratch folder there: the self-test expects them allowed on Linux and checks that they resolve inside it, and refuses `../../secrets.txt` and `//server/share/file` on every OS. Before this, the self-test failed 36/38 on Linux. In the Chapter 8 listing, `RunShellAsync` now calls `ShellRunner.BuildStartInfo` and `ShellRunner.RunAsync` instead of building the `ProcessStartInfo` inline. | v1.1.0 (companion code) |
| R03 | Ch13 · `Ch13.ApprovalWorkflow` | A | An empty line, a typo or the end of input became "approve" and finalized the document. | The review gate accepts exactly `approve`, `revise` or `reject`; anything else re-prompts (three tries), end of input leaves the review pending, and `reject` stops without finalizing. Pending and rejected runs exit with code 2. `--self-test` (10/10). | v1.1.0 (companion code) |
| R04 | Ch08 · `Ch08.ToolApproval` | A | The chapter presented approval as the fix for a non-idempotent write. An approved refund could still run twice after a retry, a resumed session or a double click. | `RefundOrder` goes through a ledger: the check and the credit happen under one lock, and refunding the same order again returns the original confirmation without a second credit. The comments explain why approval and idempotency complement each other. `--self-test` (6/6, including 50 concurrent calls for one order). | v1.1.0 (companion code) |
| R05 | Ch16 · `Ch16.ToolApproval` | A | The auto-approve rule was `amount <= 50`, so -10 and 0 were approved, and the amount was parsed with the current culture ("1.5" read as 15 on a German machine). | Only `0 < amount <= 50` is auto-approved; the amount is read as a JSON number or invariant-culture text, and anything unreadable is escalated. `--self-test` (15/15, run under de-DE). The simulated reviewer in scenario 2 rejected the $5,000 refund citing a "$1000 policy limit" that exists nowhere in the sample, and the model repeated it; the reason now cites the real $50 auto-approve limit. | v1.1.0 (companion code) |
| R07 | Ch18 · `Ch18.EvalTests`, `Ch18.FaqEval` | A | The PTO check `Contains("15")` accepted "Employees get 115 days" and "Not 15 days; employees get 20", yet it was named and described as a grounding check. | Renamed to a value check: it passes only when every stated day count is exactly 15, with two expected-fail counterexamples. FaqEval matches the expected value as a whole token. The comments say it is a lexical value check, not a faithfulness score. | v1.1.0 (companion code) |
| R14 | Ch07 · `Ch07.EntityExtraction`, `Ch07.RobustExtraction` | B | The model's `Confidence` was trusted as a calibrated number and used as a gate. A missing value became 0, values outside 0..1 (including 95 on a percent scale) passed through, and a string such as `"0.9"` was coerced into a number. | The property is `SelfReportedConfidence` (`double?`, JSON name still `confidence`, strict number handling), range-checked and labelled "self-reported, not calibrated". It can add a review warning but never clear one; an extraction is auto-processed only when no validation rule fired. RobustExtraction also flags an empty vendor. `--self-test` (16/16 and 18/18). In Chapter 7, read "gate downstream behavior on the threshold" as "let a low or invalid value add a review flag". | v1.1.0 (companion code) |
